## 一、模块结构

前端拆成 4 个文件，各管一件事。**这样拆是为了让每个文件都能单独测试**。

| 文件 | 职责 | 行数级别 |
|---|---|---|
| `index.html` | 结构骨架 | ~110 |
| `style.css` | 样式 + 双主题 | ~600 |
| `markdown.js` | Markdown 渲染（含 XSS 防护） | ~200 |
| `sse.js` | SSE 流式客户端（含中止） | ~100 |
| `store.js` | 本地存储（会话索引 / 主题 / 导出） | ~180 |
| `app.js` | 主逻辑，编排以上模块 | ~600 |

**加载顺序有依赖**：`markdown` → `sse` → `store` → `app`。写在前面的模块被后面使用。

**为什么不用打包工具**：4 个文件、无依赖、无构建。改完刷新页面即可看到效果，省掉了 npm/webpack/vite 一整套工具链。学习阶段这样最省心。

## 三、技术要点（值得学习的地方）

### 3.1 Markdown 渲染：Token 占位法

**先说朴素做法有什么 bug。** 如果先替换代码块、再替换加粗：

```
输入：  调用 `a**b**c` 即可
错误结果： 调用 <code>a<b>b</b>c</code> 即可     ← 内容被改坏了
```

代码里的 `**` 被当成了加粗标记。

**正确做法：三步走**

```
第 1 步：把代码块/行内代码「摘出来」，换成占位符   `a**b**c` → ⟦0⟧
第 2 步：对剩下的正文做加粗/斜体/链接等替换        ⟦0⟧ 不含 **，不受影响
第 3 步：把占位符换回 <code>                      ⟦0⟧ → <code>a**b**c</code>
```

这样**代码内容全程不参与正文替换**，不可能被误伤。

**顺序上还有一条铁律**：先 `esc()` 转义，再做任何解析。
否则 `innerHTML` 会让用户输入里的 `<script>` 真的执行。

**我为此写了 33 个测试**，覆盖 XSS、代码块保护、块级语法、组合场景、边界情况：

```
[1] XSS 防护          ✓ script/img/javascript: 全部被挡
[2] 代码块保护        ✓ 代码里的 ** 和 * 不被误伤
[3] 基本行内语法      ✓ 加粗/斜体/删除线/行内代码
[4] 块级语法          ✓ 标题/列表/引用/表格/分隔线
[5] 组合场景          ✓ 真实模型输出混合格式
[6] 边界情况          ✓ 空串/未闭合代码块/超长无空格串
结果: 33 通过, 0 失败
```

### 3.2 SSE 客户端：两个必须处理的坑

**坑 1：网络分片是任意的。** JSON 可能被切成两半：

```
第一片: 'data: {"type":"tok'
第二片: 'en","text":"好"}\n\n'
```

所以用 `buffer` 累积，**只处理以 `\n\n` 结尾的完整消息**，剩下的留到下一轮。

**坑 2：一个汉字占 3 字节，可能被切在中间。**

必须用 `TextDecoder.decode(value, { stream: true })`。不加 `stream:true`，半个汉字会解码成 `�`。

**坑 3（我踩到的）：`abort()` 不一定抛异常。**

这是我写测试时发现的真实问题：

> 如果中止发生在「已经收到部分数据」之后，`reader.read()` 往往**正常 resolve**（`done=true`）而不是 reject。
> 于是循环安静地结束，调用方**根本不知道是被中止了**——会误以为生成完成。

**修法**：在循环里每轮显式检查 `signal.aborted`，主动抛 `AbortError`：

```js
const abortError = () => { const e = new Error('Aborted'); e.name = 'AbortError'; return e; };

while (true) {
  if (signal?.aborted) throw abortError();      // ← 显式检查
  const { done, value } = await reader.read();
  ...
  for (const part of parts) {
    if (signal?.aborted) throw abortError();    // ← 每个事件前也检查
    ...
  }
}
```

**为什么要检查两处**：一个网络分片里可能含多个事件。如果只检查循环开头，一批事件处理到一半中止了也不会立刻停。

### 3.3 本地存储与服务端记忆的对齐

**问题**：后端记忆现在存在**进程内字典**里（`memory_backend: inproc`）。
**容器一重启，服务器端记忆就全没了**，但 localStorage 不会消失。

如果只信本地存储，就会出现「列表里有一段会话，点进去却是空的」——用户以为坏了。

**解法**：`Store.reconcile()` 用服务器返回的 `/api/sessions` 校正本地索引：

| 情况 | 处理 |
|---|---|
| 服务器有、本地没有 | 补进本地（换了浏览器，或本地被清过） |
| 服务器有、本地也有 | 以服务器的时间和轮数为准（那是真相） |
| **本地有、服务器没有** | **从本地剔除**（记忆已丢，避免点进去是空的） |

**并且要保护用户的命名**：本地改过名字的（标记 `renamed: true`）不被服务器标题覆盖。

**这个设计的价值**：等以后接入 Upstash Redis（记忆持久化），这套对齐逻辑**一个字都不用改**，它会自动变得更准。

### 3.4 流式渲染的性能优化

一次回答可能有上百个 token。如果每个 token 都重跑一遍 Markdown 解析，会明显卡顿。

所以用 `requestAnimationFrame` 节流 —— **每帧最多渲染一次**：

```js
append(token) {
  raw += token;
  if (renderTimer) return;                    // 本帧已经排过队了，跳过
  renderTimer = requestAnimationFrame(() => {
    renderTimer = null;
    body.innerHTML = MD.render(raw);          // 每帧只渲染一次
    ...
  });
}
```

**注意收尾时要 `cancelAnimationFrame`**，否则最后几个 token 可能来不及渲染。

### 3.5 颜色变量化实现主题切换

```css
:root { --bg: #0f1115; --text: #e6e9ef; ... }          /* 深色 */
:root[data-theme="light"] { --bg: #f6f7f9; ... }        /* 浅色只覆盖颜色 */
```

**只覆盖颜色变量，布局和尺寸完全不动。** 换主题只需要十几行 CSS，不用写两套样式。

## 四、新增的后端接口

| 方法 | 路径 | 作用 |
|---|---|---|
| `GET` | `/api/sessions` | 列出所有会话（含轮数、最后活动时间、第一个问题） |
| `DELETE` | `/api/sessions` | 清空所有会话 |

`first_question` 是给前端当会话标题用的 —— 用户自己一看就知道那段对话在聊什么。

**实现上的一个细节**：Redis 分支用 `scan_iter` 而不是 `keys()`。
`keys()` 会**阻塞 Redis**（要遍历整个键空间），在生产环境是危险操作。`scan_iter` 是游标式的，安全。

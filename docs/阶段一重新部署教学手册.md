## 1.2 关键概念：这是「突发型」机器

`Standard_B2ts_v2` 里的 **`t`** 代表 **burstable（突发型）**。
它和普通云服务器最大的区别是：**CPU 算力是按"额度"借给你的，不是无限供给的。**

来源：[Microsoft Azure 官方规格文档](https://raw.githubusercontent.com/MicrosoftDocs/azure-compute-docs/refs/heads/main/articles/virtual-machines/sizes/general-purpose/bsv2-series.md)

| 项目 | 数值 |
|---|---|
| 基础 CPU 性能 | **20%** |
| 初始额度 | 60 credits |
| 额度累积速度 | **24 credits/小时** |
| 额度上限 | 576 credits |
| 本地临时盘 | **无**（所有磁盘 IO 走网络） |

### 额度算术（这是理解一切性能问题的钥匙）

公式来源：[Azure B 系列 CPU 额度模型](https://docs.azure.cn/zh-cn/virtual-machines/sizes/b-series-cpu-credit-model)

```
每分钟净累积额度 = ((基础CPU% × vCPU数) − (实际CPU% × vCPU数)) / 100
```

代入你的机器（基础 20%，2 vCPU）：

| 机器状态 | 计算过程 | 结果 |
|---|---|---|
| 完全空闲 | `((20×2) − (0×2)) / 100` | **+0.4 / 分钟** → +24 / 小时 |
| 满负载 100% | `((20×2) − (100×2)) / 100` | **−1.6 / 分钟** → **−96 / 小时** |

**关键结论：满负载跑 1 小时，需要空闲 4 小时才能把额度补回来。**

用完额度后，机器会被**限速到 20%**。症状是：**内存看着没满，但服务莫名变得极慢。**

### 由此推出两条设计原则（贯穿全文）

> **原则一：内存是硬瓶颈，CPU 是可以"借"的。**
> 短时任务（`apt install`、`docker build`）能突发用满，没问题。
> 但**长期持续的重负载会被限速**。

> **原则二：swap 换页会消耗 CPU 额度，不能把 swap 当内存用。**
> 换页本身要 CPU。如果程序真把 891 MiB 用满、频繁 swap 抖动，
> 会迅速烧光每小时仅有的 24 额度 → 被限速 → 服务卡死。
> 所以 swap 只作**抗瞬时峰值的安全垫**，绝不作为可用内存来规划。

## 1.3 由规格推出的三个技术决策

这三条是对原手册的重要修正，**理解它们比记住命令更重要**：

### 决策 1：不用本地大模型，改用云端 API

原手册要求「Llama.cpp 本地 Qwen-7B 4bit」。

**问题：** Qwen-7B 即使 4bit 量化，模型权重也要约 **4.4 GB**。
你的可用内存是 **891 MiB** —— **差 5 倍**。连加载这一步都过不去，必然被 OOM Killer 杀掉。

**注意：这跟 CPU 是 2 核还是 1 核无关，卡住的是内存。** 换 CPU 配置不解决问题。

### 决策 2：向量化也用 API，不在本地跑 embedding 模型

本地跑 `all-MiniLM-L6-v2` 这类 embedding 模型，加上 onnxruntime 运行时，
常驻内存要 **400-500 MB** —— 在 891 MiB 机器上等于吃掉一半以上。

后果：剩下的内存不够 FastAPI + Chroma 用 → 持续换页 → 烧光 CPU 额度 → 被限速。

**改用云端 API 后，这部分内存占用接近零。**

### 决策 3：Chroma 用嵌入式模式，不起独立容器

独立 Chroma 容器常驻要 200MB+。改用 `langchain-chroma` 的
`PersistentClient` 后，向量库跑在 API 进程内，数据照样持久化到磁盘，
**省下一整个容器的内存开销**。

> **阶段三预警（提前告诉你，避免走弯路）：**
> 到阶段三如果要跑本地模型，**这台机器做不到**。原因不只是内存 ——
> 本地 LLM 推理是**持续满负载**，烧额度速度 **−96/小时**，而补充只有 **+24/小时**。
> 额度必然耗尽 → 被限速到 20% → 慢到不可用。
> 到时应升级到 **B2ls_v2**（2 vCPU / **4 GiB**，同系列可直接改规格）。

# 第三部分：第一步 —— 认清现状（不要跳过）

**学习要点：** 部署的第一条命令永远不是"安装"，而是"查看"。
你必须在动手前知道机器现在是什么样，否则出问题时你无法判断是"本来就这样"还是"我改坏了"。

## 3.1 关键目录权限（**这条最重要，直接决定后面成败**）

```bash
ls -ld /home/azureuser
```

**为什么必须看这个：** 后面我们要把宿主机的目录挂载进 Docker 容器
（叫 **bind mount**）。Linux 的权限规则要求：**进程必须能"穿越"路径上的每一级目录**，
才能访问最终的目标目录。

**预期输出：**
```
drwxr-x--- 5 azureuser azureuser 4096 ... /home/azureuser
```

**读懂它：** `drwxr-x---` 的含义是——
- 属主 `azureuser`：`rwx`（可读写进入）
- 同组用户：`r-x`（可读进入）
- **其他人：`---`（完全无权）**

**这会产生什么后果？** 我们的容器里如果以镜像内自建的用户（uid 10001）运行，
它既不是 `azureuser` 也不在 `azureuser` 组里，属于"其他人"→ **连这个目录都进不去**
→ bind mount 报 `Permission denied`。

**这就是后面 `docker-compose.yml` 里要写 `user:` 指令的根本原因。**
不是可有可无的配置，是必须的。

# 第四部分：基础环境加固

## 4.1 确认 swap 可用（已配置，只需验证）

```bash
free -h
swapon --show
grep swap /etc/fstab
```

**为什么重要：** 后面 `docker build` 装依赖时，pip 的依赖解析会瞬时吃掉几百 MB。
没有 swap，构建会被内核 **OOM Killer** 直接杀掉 —— 症状是莫名其妙的
`Killed` 或 `exit code 137`，初学者极难排查。

**预期输出：**
```
               total        used        free
Mem:           891Mi        ...        ...
Swap:          1.0Gi        ...        ...

NAME      TYPE SIZE USED PRIO
/swapfile file 1024M ...  -2

/swapfile none swap sw 0 0      ← fstab 里有这行，代表开机自动挂载
```

**如果 swap 不存在**（你现在有，这一步只是学会怎么查），创建方式是：

```bash
sudo fallocate -l 2G /swapfile     # 创建 2GB 文件
sudo chmod 600 /swapfile           # 设为只有 root 可读写（否则系统拒绝启用）
sudo mkswap /swapfile              # 格式化为 swap 格式
sudo swapon /swapfile              # 立即启用
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab   # 永久生效
```

**为什么 `chmod 600` 不能省：** swap 文件里会写入内存中的敏感数据
（包括你刚才输入的 API Key）。权限放开等于泄露。

**调整 swappiness（可选但推荐）：**

```bash
sudo sysctl vm.swappiness=10
echo 'vm.swappiness=10' | sudo tee -a /etc/sysctl.conf
```

**为什么：** 默认值是 60，比较激进，会让热数据被换出到 swap。
我们的原则二是"尽量别换页"，所以把它调低到 10。

## 4.2 确认 Docker 引擎健康

```bash
docker --version
docker compose version
docker info | grep -E "Server Version|Storage Driver|Docker Root Dir"
```

**预期：** 版本见第二部分表格；`Storage Driver` 是 `overlayfs`。

**为什么要确认 compose 是 v2：** `docker compose`（v2，带空格，是插件）
和 `docker-compose`（v1，带横线，是独立的 Python 程序）**是两回事**。
v1 早已停止维护。本手册全程用 `docker compose`（带空格）。

```bash
# 验证 Docker 真的能跑容器
docker run --rm hello-world
```

**为什么要跑这个：** 这是 Docker 官方的最小验证镜像。
它能跑通，说明引擎、存储驱动、网络都正常。
**这是部署前最有价值的 10 秒钟。**

## 4.3 配置 Docker 日志上限

```bash
sudo mkdir -p /etc/docker
sudo tee /etc/docker/daemon.json > /dev/null <<'EOF'
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}
EOF

sudo systemctl restart docker
cat /etc/docker/daemon.json
docker info | grep -A2 "Logging Driver"
```

**为什么必须做：** Docker 默认**不限制**容器日志大小。
一个不断报错的容器能在几天内把日志写到几个 GB，**悄悄吃满磁盘**。
这个配置把每个容器的日志限制在 10MB × 3 个文件 = 最多 30MB。

**注意 `systemctl restart docker` 的风险：** 如果在 SSH 会话里重启 Docker
**且**你的 SSH 连接依赖于某个容器，就会断线。
本例中 SSH 是系统自带服务，重启 Docker 是安全的。但在生产环境要谨慎 ——
**能用 `reload` 就不用 `restart`**。

# 第五部分：系统瘦身（可选，理解即可）

这台机器之前有一些用不上的服务在占内存。

```bash
# 看谁在吃内存
ps aux --sort=-%mem | head -10

# 看 fwupd 状态
systemctl is-active fwupd.service
systemctl is-enabled fwupd.service
```

**`fwupd` 是什么：** 固件更新服务。它是为**物理机**设计的，
用于更新主板/硬盘固件。**云虚拟机没有固件可更新**，
但它仍会周期性运行，实测曾占用 **43.9% CPU** 和约 20MB 内存。

```bash
# 停用并屏蔽（已执行过，你只需理解）
sudo systemctl stop fwupd.service
sudo systemctl mask fwupd.service fwupd-refresh.timer fwupd-refresh.service
```

**`stop` 和 `mask` 的区别（重要概念）：**
- `stop` = 现在停掉，但下次开机还会启动
- `disable` = 开机不启动，但可以手动启动
- `mask` = **彻底封死**（软链接到 `/dev/null`），连手动都启动不了

**对 891 MiB 的机器来说，省下 20MB 内存是有意义的。**

**同类可考虑停用的服务：**

```bash
sudo systemctl stop ModemManager.service    # 云主机没有调制解调器
sudo systemctl disable ModemManager.service
```

**但要谨慎：** 有些服务看着没用，实际是系统依赖（比如 `multipathd` 涉及存储路径）。
**不要批量乱停服务**，每次只停一个，然后验证系统正常。

# 第六部分：创建项目

## 6.1 建立目录结构

```bash
mkdir -p ~/phase1-rag/backend/app
mkdir -p ~/phase1-rag/data/chroma
mkdir -p ~/phase1-rag/data/uploads
cd ~/phase1-rag
```

**为什么这样分层：**

| 目录 | 作用 |
|---|---|
| `backend/app/` | Python 源码 |
| `data/chroma/` | 向量库数据（**清空 = 知识库清零**） |
| `data/uploads/` | 上传的原始文档 |

**为什么数据和代码要分开：** 因为 `data/` 会被挂载进容器。
代码随镜像走，数据随卷走 —— 这样容器重建（换代码）不会丢知识库。

## 6.2 创建后端依赖清单

```bash
cat > ~/phase1-rag/backend/requirements.txt <<'EOF'
fastapi>=0.115,<1
uvicorn[standard]>=0.30,<1
python-multipart>=0.0.9
pydantic>=2.7,<3
pydantic-settings>=2.3,<3

langchain>=0.3,<2
langchain-core>=0.3,<2
langchain-community>=0.3,<2
langchain-text-splitters>=0.3,<2
langchain-chroma>=0.2,<2
chromadb>=0.5,<2

pypdf>=4.2

langchain-openai>=0.2,<2

redis>=5,<7
httpx>=0.27
EOF
cat ~/phase1-rag/backend/requirements.txt
```

**为什么用版本区间（`>=x,<y`）而不是写死版本：**
- 写死（`==1.2.3`）→ 可复现，但容易撞上已废弃的版本
- 区间 → 每次构建拿到最新兼容版，但**可能引入破坏性变更**

**本项目的选择理由：** 你还在学习阶段，需要"能装上"。
代价是我必须验证代码在新版本下能跑 —— 实测发现 LangChain 实际解析到
**1.4.3**（不是我预期的 0.3.x），已逐一验证 API 兼容。

**关键点：`langchain-openai` 一个包同时覆盖 chat 和 embedding**，
因为阿里百炼两者都走 OpenAI 兼容协议。这比装两套 SDK 干净得多。

## 6.3 创建 Dockerfile

```bash
cat > ~/phase1-rag/backend/Dockerfile <<'EOF'
FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1 \
    PIP_DISABLE_PIP_VERSION_CHECK=1

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app ./app

RUN useradd -m -u 10001 appuser && \
    mkdir -p /app/data/chroma /app/data/uploads && \
    chown -R appuser:appuser /app
USER appuser

EXPOSE 8000

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "1", "--timeout-keep-alive", "30"]
EOF
cat ~/phase1-rag/backend/Dockerfile
```

**逐条讲解每个决策：**

| 写法 | 为什么 |
|---|---|
| `FROM python:3.12-slim` | slim 版比完整版小约 700MB。1 GiB 内存机器上，镜像小 = 磁盘和内存压力都小 |
| `PYTHONDONTWRITEBYTECODE=1` | 不生成 `.pyc` 缓存。容器里没必要，还能避免权限问题 |
| `PYTHONUNBUFFERED=1` | **让日志实时输出**。不加的话 `docker logs` 看不到实时日志，排查困难 |
| `PIP_NO_CACHE_DIR=1` | pip 不缓存下载的包，省磁盘 |
| **先 `COPY requirements.txt` 再 `COPY app`** | ← **这是关键技巧。** Docker 按层缓存：只要 `requirements.txt` 没变，改代码后重建**不会重装依赖**，从几分钟变成几十秒 |
| `useradd -u 10001` | 非 root 运行，安全最佳实践 |
| `--workers 1` | **单 worker。** 瓶颈是内存（891 MiB）和网络 IO，不是 CPU。多开会成倍放大内存，吞吐几乎不变 |

## 6.4 创建 `docker-compose.yml`

```bash
cat > ~/phase1-rag/docker-compose.yml <<'EOF'
services:
  api:
    build:
      context: ./backend
      dockerfile: Dockerfile
    image: phase1-rag-api:0.1.0
    container_name: rag-api
    restart: unless-stopped
    user: "${COMPOSE_USER:-1000:1000}"
    env_file:
      - .env
    ports:
      - "127.0.0.1:8000:8000"
    volumes:
      - ./data/chroma:/app/data/chroma
      - ./data/uploads:/app/data/uploads
    mem_limit: 600m
    memswap_limit: 1600m
    environment:
      - PYTHONUNBUFFERED=1
      - OMP_NUM_THREADS=2
      - OPENBLAS_NUM_THREADS=2
      - MKL_NUM_THREADS=2
      - TOKENIZERS_PARALLELISM=false
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request,sys; sys.exit(0 if urllib.request.urlopen('http://127.0.0.1:8000/health', timeout=3).status==200 else 1)"]
      interval: 30s
      timeout: 5s
      retries: 5
      start_period: 60s
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
EOF
export COMPOSE_USER="$(id -u):$(id -g)"
docker compose -f ~/phase1-rag/docker-compose.yml config | head -30
```

**每一行为什么这么写：**

### `user: "${COMPOSE_USER:-1000:1000}"` ← 最关键的一行

**为什么必须有：** 回到 3.1 节的发现 —— `/home/azureuser` 权限是 `750`。
如果容器用镜像内的 `appuser`（uid 10001）运行，它连这个目录都进不去，
bind mount 直接 `Permission denied`。

**语法讲解：** `${COMPOSE_USER:-1000:1000}` 是 **shell 参数扩展** ——
如果环境变量 `COMPOSE_USER` 有值就用它，否则用默认值 `1000:1000`。

```bash
export COMPOSE_USER="$(id -u):$(id -g)"   # 先设置好，再跑 compose
```

> **⚠️ 一个真实的坑（我踩过）：**
> 直觉写法是 `export UID="$(id -u)"`，但 **bash 里 `UID` 是只读变量**，
> 这行会报 `readonly variable` 错误。
> 所以这里用自定义变量名 `COMPOSE_USER`，一次传 `uid:gid`。

### `mem_limit: 600m` / `memswap_limit: 1600m`

**为什么必须设：** 891 MiB 的机器上，如果某个容器内存泄漏，
会拖垮**整台机器**。设上限后，越界的容器自己被杀，系统保住。

**数字怎么来的：** 系统（OS + Docker）常驻约 250MB，留给业务 600MB，
剩余靠 swap 兜底。`memswap_limit` 允许借用 swap 抗瞬时峰值。

### `ports: "127.0.0.1:8000:8000"`

**为什么不是 `8000:8000`：** 后者会监听 `0.0.0.0`，**等于把 API 暴露到公网**。
而我们的 API 携带 API Key，暴露后可能被盗用刷额度。

写成 `127.0.0.1:8000:8000` 表示**只监听本机**，
外部访问要走 SSH 隧道（见第八部分）。

### `volumes: ./data/...`

**为什么：** 容器删除后数据就没了。挂载出来，容器重建不丢知识库。

### `healthcheck`

**为什么：** `docker compose ps` 里的 `Up` 只代表"进程还活着"，
不代表"服务真的能用"。健康检查会真的去请求 `/health`，
只有返回 200 才算健康。**这是区分"启动"和"可用"的关键。**

### `environment` 里的线程变量

**为什么是 2：** 你有 2 vCPU。但**不要设更大** ——
1 GiB 内存机器上超配线程只会加剧换页 → 烧 CPU 额度。

## 7.1 创建配置模板

```bash
cat > ~/phase1-rag/.env.example <<'EOF'
```

**为什么要分 `.env.example` 和 `.env` 两个文件：**
- `.env.example` 是**模板**，不含真实密钥，**可以安全提交到 git**
- `.env` 是**真实配置**，含密钥，**绝不能提交**

这是行业惯例。养成这个习惯很重要。

## 7.2 生成真实配置并锁定权限

```bash
cd ~/phase1-rag
cp .env.example .env
chmod 600 .env
ls -la .env
stat -c '%a %n' .env
```

**为什么 `chmod 600` 是必须的：** `.env` 里有 API Key，等价于密码。
`600` 表示只有属主可读写，其他任何人都不能碰。

**预期：** `600 /home/azureuser/phase1-rag/.env`

## 7.3 理解阿里百炼（DashScope）的关键参数

**为什么选百炼：** 一个 key 同时覆盖 chat 和 embedding，且都是 OpenAI 兼容协议。

来源：[OpenAI兼容-Embedding 官方文档](https://help.aliyun.com/zh/model-studio/embedding-interfaces-compatible-with-openai)

| 参数 | 值 | 说明 |
|---|---|---|
| Base URL | `https://dashscope.aliyuncs.com/compatible-mode/v1` | 固定 |
| chat 模型 | `qwen-plus` | 质量/成本平衡；省钱可换 `qwen-turbo` |
| embedding 模型 | `text-embedding-v4` | Qwen3-Embedding 系列 |
| 支持维度 | 2048/1536/**1024(默认)**/768/512/256/128/64 | 我们选 1024 |

### ⚠️ 坑 1：embedding 单次最多 10 行输入

**这是百炼的硬限制。** 而 langchain 的 `OpenAIEmbeddings` **默认 `chunk_size=1000`**。

**如果你不显式改成 10，上传稍大的文档就会直接报错。**
这是最容易踩、也最难自己想到的坑 —— 因为错误信息不会告诉你"是批次大小问题"。

**本项目做了双重防护：**

1. `.env` 里 `EMBEDDING_BATCH_SIZE=10`（传给 langchain）
2. **应用代码里再显式分批** —— 即使有人手改配置调大了，也不会整批失败

### ⚠️ 坑 2：稀疏向量会静默返回空

官方文档明确：`output_type=sparse` 在 OpenAI 兼容模式下会返回
**HTTP 200 但 embedding 为空** —— 即"成功"的假象。

**我们不使用这个参数**，但如果你以后遇到「入库显示成功却检索不到内容」，
这是第一嫌疑对象。

### 坑 3：chromadb 集合名至少 3 字符

chromadb 1.x 要求集合名长度 **3-512**，且符合 `[a-zA-Z0-9._-]`，
必须以字母或数字开头结尾。

本项目用 `phase1_docs`（合法）。**如果你改成 `t` 就会报错** ——
错误信息是 `InvalidArgumentError: Validation error: name:`，
初学者很难联想到"是名字太短"。

## 7.4 申请并填入 API Key

**申请步骤：**

1. 浏览器打开 https://bailian.console.aliyun.com/
2. 开通「大模型服务平台百炼」
3. 找到 **API-KEY 管理** → **创建 API-KEY** → 复制

### ⚠️ key 有两种格式，别被搞混

| 格式 | 样子 | 说明 |
|---|---|---|
| 通用密钥 | `sk-` + 32 位十六进制 | 最常见的形态，网上教程都是这个 |
| **业务空间密钥** | **`sk-ws-` 开头，较长（117 字符）** | 本次部署实际拿到的就是这种 |

**本次部署实测：`sk-ws-` 开头的业务空间密钥，
用默认的 `DASHSCOPE_BASE_URL` 完全可用**，不需要任何额外配置。

百炼官方文档提到业务空间可以迁移到专属域名：
```
https://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/compatible-mode/v1
```
**但我实测确认：默认域名照常工作，不必迁移、不必填 WorkspaceId。**

> **教学要点：** 官方文档里的「建议迁移」「推荐使用」这类措辞，
> 不代表旧方式不可用。**看到这类字样时，先实测再决定要不要改配置** ——
> 盲目跟着改可能引入不必要的问题（这里就会多一个 WorkspaceId 要维护）。
>
> 官方原话其实是「现有域名仍可正常使用」，实测印证了这一点。

**填入：**

```bash
nano ~/phase1-rag/.env
```

只改**一行**：

```ini
DASHSCOPE_API_KEY=sk-你的真实key
```

保存：`Ctrl+O` → 回车 → `Ctrl+X`。

**为什么用 `nano` 而不是 `echo` 追加重定向：**
`.env` 里已经有一行 `DASHSCOPE_API_KEY=`（空的）。
如果用 `echo "DASHSCOPE_API_KEY=xxx" >> .env`，
会变成**两行同名变量**，而后一行才是生效的 ——
这种"看似成功实则行为诡异"的情况很难排查。
**用编辑器原地替换那一行，是最安全的做法。**

### 🔐 写入后请立刻做两件事

**① 确认权限仍是 600**

```bash
stat -c '%a %n' ~/phase1-rag/.env
```

**预期：** `600 /home/azureuser/phase1-rag/.env`

有些编辑器保存时会重建文件，可能把权限重置成 644 → **密钥就变成同机其他用户可读了**。

**② 删除任何含密钥的备份副**（如果你创建过）

```bash
ls -la ~/phase1-rag/ | grep -i "env"
```

**本次部署中我犯过这个错：** 为了避免改坏配置，我先 `cp .env .env.bak`
再编辑。**但 `.env.bak` 里含明文密钥**，事后必须删掉：

```bash
rm -f ~/phase1-rag/.env.bak
```

> **教训：** 备份是好习惯，但**备份敏感文件时要意识到"备份也是敏感文件"**。
> 要么备份后立刻改权限（`chmod 600 .env.bak`），
> 要么确认成功后立刻删除。**不要让它留在服务器上。**

> **安全提醒：** 不要把 key 贴到任何聊天/issue/截图里。
> 如果怀疑泄露，立刻去百炼控制台**删除该 key 并重建**。

**`REDIS_URL` 保持留空是正常的：** 应用代码会自动降级为进程内记忆
（`memory_backend: inproc`），服务照常可用。等以后注册了 Upstash 再填，
**代码一行都不用改** —— 这是刻意设计的降级路径。

# 第八部分：构建与启动

## 8.1 构建镜像

```bash
cd ~/phase1-rag
export COMPOSE_USER="$(id -u):$(id -g)"
docker compose build
```

**预期：** 本次实测 **76 秒**（12:43:51 → 12:45:07）。
其中 pip 装依赖约 40 秒、镜像导出约 34 秒。镜像 958MB。

**为什么这么快：** 这就是 §6.3 里「先 COPY requirements.txt 再 COPY app」
那个分层技巧的价值。如果顺序写反（先 COPY app），改一行代码就要重装全部依赖，
每次都得等几分钟。

**盯内存（另开一个 SSH 窗口）：**

```bash
watch -n 5 free -h
```

**为什么盯：** 如果在构建中看到 `available` 掉到几 MB、`Swap` 用量飙升，
说明内存吃紧。若此时构建被 `Killed`，就是 OOM —— 需要确认 swap 正常。

**关于 CPU 额度：** 构建是短时高负载，会消耗额度换突发性能。
开机初始有 60 额度，够跑完一次。

> **⚠️ 不要反复重启构建。** 每次重试都消耗额度，耗尽后会被限速到 20%，
> 表现为"越试越慢"，让人误以为是网络问题。

## 8.2 启动服务

```bash
docker compose up -d
```

**参数讲解：**
- `up` = 创建并启动
- `-d` = detached，后台运行（不加的话日志会占满你的终端，`Ctrl+C` 会停掉服务）

> **⚠️ 别忘了 `export COMPOSE_USER`！**
> 每个新开的 SSH 窗口，`COMPOSE_USER` 都**没有设置**。
> 如果忘了 export 就直接 `docker compose up -d`，
> `${COMPOSE_USER:-1000:1000}` 会回退到默认值 `1000:1000` ——
> 本例中恰好正确（你的 uid 就是 1000），所以不会报错。
> **但如果哪天 uid 不是 1000，就会静默地以错误身份运行，导致目录写不进去。**
> 养成习惯：**每次开新窗口，先 export 再操作。**

## 8.3 验证启动状态

```bash
docker compose ps
```

**读懂输出：** 注意 `STATUS` 列。你要看到 `Up ... (healthy)`。
**只有 `Up` 而没有 `healthy`，不代表服务可用。**

**本次实测输出：**
```
NAME      IMAGE                  COMMAND               SERVICE   STATUS
rag-api   phase1-rag-api:0.1.0   "uvicorn app.main:ap…" api      Up 6 seconds (healthy)
```

**本次启动耗时：9 秒进入 healthy。**（`start_period: 60s` 是给足余量的上限）

**验证开机自启是否生效：**

```bash
docker inspect rag-api --format 'restart: {{.HostConfig.RestartPolicy.Name}}'
```

**预期：** `restart: unless-stopped`

**为什么这条重要：** 它代表**服务器重启后容器会自动拉起**。
没有这个策略的话，Azure 维护或你手动重启机器后，服务就静默地不在了 ——
而你可能几天后才发现。`unless-stopped` 的语义是
「除非我明确 `docker stop`，否则总是自动启动」，这正是我们要的。

```bash
# 看日志
docker compose logs -f api      # Ctrl+C 退出查看，不会停服务
```

**预期看到（本次实测的完整日志）：**
```
INFO:     Started server process [1]
INFO:     Waiting for application startup.
INFO:     Application startup complete.
INFO:     Uvicorn running on http://0.0.0.0:8000 (Press CTRL+C to quit)
```

**注意最后那行 `0.0.0.0:8000` 不要误解。**
它表示 **uvicorn 在容器内部**监听所有网卡。
但 `docker-compose.yml` 里的 `ports: "127.0.0.1:8000:8000"` 决定了
**宿主机只在本机回环地址上映射这个端口**。可以用下面命令确认：

```bash
sudo ss -tlnp | grep 8000
```

**本次实测输出：**
```
LISTEN 0 4096 127.0.0.1:8000 0.0.0.0:*  users:(("docker-proxy",pid=42652,fd=7))
```

**看到 `127.0.0.1:8000` 而不是 `0.0.0.0:8000`** —— 说明公网确实访问不到，
API Key 没有暴露。**这是必须确认的一点。**

**如果没看到，按顺序查：**

```bash
docker compose logs --tail 50 api     # 真实报错在这里
```

```
- 技术总负责人：林可欣
```

**关键检查三件事：**

1. **答案正确** —— 陈思远 / 林可欣 / 487 万元，这些**只存在于你的文档里**
2. **带引用标注** —— 答案末尾有 `[来源1]`
3. **`sources` 数组非空** —— 本次返回 2 个 chunk，

`0.6452` 表示第一个 chunk 高度相关，`0.3227` 表示第二个相关性较弱但仍在

**一个容易忽略的细节：** 注意答案里三个事实**都标注了 `[来源1]`**，
因为三个事实都在第一个 chunk 里（文档开头的基本信息段）。
如果它们分散在不同 chunk，你会看到 `[来源1][来源2]` 这样的多标注。

## 9.6 验证「不编造」（RAG 质量的核心）

这一步要做**两个**测试，因为难度不同。

### 测试 A：文档里完全没有的主题（简单）

```bash
curl -s -X POST localhost:8000/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"question":"文档里提到的量子计算机型号是什么？","session_id":"test-002"}' \
  | python3 -c "import sys,json; d=json.load(sys.stdin); print('答案:', d['answer']); print('来源数:', len(d['sources']))"
```

（你的测试文档里当然没有量子计算机。）

**本次实测：**
```
答案: 知识库中未找到相关内容
来源数: 2
```

### 测试 B：**「半个有依据」的诱导**（困难，但更重要）

```bash
curl -s -X POST localhost:8000/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"question":"蓝鲸计划的运维工程师孙立的手机号是多少？","session_id":"test-003"}' \
  | python3 -c "import sys,json; d=json.load(sys.stdin); print('答案:', d['answer']); print('来源数:', len(d['sources']))"
```

**为什么这个测试更狠：** 你的文档里**确实**写了「运维工程师 | 1 | 孙立」，
但**全文没有手机号**。

这构成了最难抵抗的诱导：**问题的一半有真实依据**。
模型很自然会想「孙立这个人检索到了，那我补一个手机号吧」——
这就是幻觉的典型成因。

**本次实测：**
```
答案: 知识库中未找到相关内容
来源数: 2
```

**✅ 模型抵抗住了。** 这比测试 A 有说服力得多。

### 关于 `来源数: 2` 这个细节

注意两题的 `sources` 都返回了 **2 个 chunk**，答案却是"未找到"。

**这不是矛盾，反而说明设计是对的：**
向量检索**总会**返回 Top-K 结果（只要知识库非空），
因为余弦相似度总能算出一个分数 —— 即使内容无关（本次测试 A 的分数就很低）。

**真正的判断发生在 LLM 这一层** —— 它读了这些 chunk，
发现里面没有答案，于是按 system prompt 的约束老实说"未找到"。

**这正是 `rag.py` 里那个 prompt 约束的价值：**
> 如果参考资料中没有相关信息，直接回答"知识库中未找到相关内容"，不要编造。

**如果没有这句约束**，模型看到"检索到了孙立这个运维工程师"，
很可能就顺口编一个手机号出来。

### 补充验证：文档删除（本次实测）

```bash
curl -s -X DELETE localhost:8000/api/documents/fa235aa8e6b1 | python3 -m json.tool
curl -s localhost:8000/api/documents | python3 -m json.tool
```

**本次实测：**
```json
{ "deleted_chunks": 2 }
{ "documents": [] }
```

**为什么这条要测：** 它验证了入库时写入的 `doc_id` 元数据**真的有用** ——
删除时靠它精确找回该文档的所有 chunk，不会误删别的文档。

### 如果它开始编造，怎么排查

| 可能原因 | 怎么确认 |
|---|---|
| 检索没命中（该文档没入库） | `curl localhost:8000/api/documents` 看文档在不在 |
| 检索命中了但内容不相关 | 看返回的 `sources[].score` 和 `preview` |
| prompt 约束被绕过 | `docker compose logs api` 看实际拼进去的 context |
| 模型本身不听话 | 换 `LLM_MODEL=qwen-max` 试（约束遵循能力更强） |

**最有效的排查手段是看 `sources[].preview`** ——
它直接显示"模型到底看到了什么"。如果 preview 里根本没有答案，
那问题在检索；如果 preview 里有答案但模型没答对，问题在生成。

## 排查内存与 CPU 额度

```bash
free -h                    # 内存 + swap
vmstat 1 5                 # 重点看 si/so 两列（swap 换入换出）
                           # 持续非 0 = 正在换页 = 正在烧 CPU 额度
top -bn1 | head -20        # CPU 占用排行
ps aux --sort=-%mem | head -10   # 内存占用排行
docker stats --no-stream
```

**Azure 门户看额度：** VM → 指标(Metrics)，加这三个：
- `CPU Credits Remaining` ← **接近 0 就是被限速了**
- `CPU Credits Consumed`
- `Percentage CPU`

**额度耗尽的自救顺序：**
1. 停掉重负载，让机器空闲攒额度（最有效，但 4 小时才能补 1 小时）
2. 减少换页：降 `RETRIEVAL_TOP_K`，不并发上传大 PDF
3. `docker stats` 确认没有失控容器
4. 重启机器可重置初始额度到 60（**治标，别依赖它循环刷**）

# 第十一部分：故障排查对照表

| 现象 | 根本原因 | 解决 |
|---|---|---|
| 构建中途 `Killed` / `exit code 137` | 内存不足，被 OOM Killer 杀 | `free -h` 确认 swap 在用 |

| `vmstat` 的 `si`/`so` 持续非 0 | 持续换页，正在烧 CPU 额度 | 降 `RETRIEVAL_TOP_K`，别并发传大 PDF |

| `Permission denied` 挂载目录 | 容器 UID 与宿主机目录权限不符 | 确认 `COMPOSE_USER="$(id -u):$(id -g)"` 已 export |
| `permission denied /var/run/docker.sock` | docker 组权限没生效 | `newgrp docker` 或重连 SSH |
| `docker: command not found` | PATH 问题 | `which docker`，检查 `/usr/bin/docker` |
| 容器 `Up` 但不 `healthy` | 启动慢或依赖报错 | `docker compose logs api` 看真实错误 |
| Embedding 维度与配置不符 | `EMBEDDING_DIM` 与实际返回不一致 | 改 `.env`，**删 `data/chroma` 重新入库** |
| 上传 PDF 后 `chunks: 0` | 扫描版 PDF（无文字层） | 先 OCR，或改用文本版 |
| 改了 `.env` 但没生效 | 环境变量在容器启动时注入 | `docker compose up -d --force-recreate` |

# 第十二部分：学习要点总结

## 12.1 思维方式

1. **先看再动。** 每条"安装"命令前，先跑对应的"查看"命令建立基线。
2. **区分"启动"和"可用"。** `Up` ≠ `healthy`；`healthy` ≠ 密钥有效。
   要分层验证，每层都测。
3. **理解数量级，不要硬扛。** 4.4GB 权重 vs 891MiB 内存 —— 差 5 倍时，
   优化配置没有意义，必须换方案。
4. **报错时先分清"是环境问题还是代码问题"。** 我在这个项目里就误判过一次：
   看到 Chroma 报"无法打开数据库"，以为是代码权限 bug，
   实际是**我的测试脚本**用了非法集合名。**看错对象比代码 bug 更浪费时间。**

## 12.2 云服务器特有的概念

| 概念 | 要点 |
|---|---|
| **突发型实例** | CPU 靠额度借，用超了被限速。算力不是无限的 |
| **CPU 额度** | 满负载 1 小时 = 需要空闲 4 小时补回 |
| **内存 vs swap** | swap 换页消耗 CPU，低配机器上不能当内存用 |
| **bind mount 权限** | 进程要能穿越路径上每一级目录。父目录 `750` 会挡住非属主 |
| **OOM Killer** | 内存耗尽的终极处理方式 —— 直接杀进程。表现为 `exit 137` |
| **无本地临时盘** | 该机型所有磁盘 IO 走网络，延迟高于本地盘 |

## 12.3 工程习惯

- **配置与代码分离**（`.env` / `.env.example`）
- **密钥不落代码库**，权限 `600`
- **Dockerfile 分层优化**（先依赖后代码，利用缓存）
- **容器资源限制**（`mem_limit` 不是可选项）
- **健康检查**区分"活着"和"能用"
- **默认只监听 127.0.0.1**，需要时再显式放开
- **传输文件后校验哈希**，而不是"看起来一样"
- **备份敏感文件时，备份本身也是敏感文件**

## 12.4 如何把环境重置回起跑线（想重做一遍时用）

如果你想**从零重做一遍部署**来巩固记忆，按顺序执行：

```bash
cd ~/phase1-rag

# 1) 停止并删除容器（保留 data/ 和代码）
docker compose down

# 2) 删除镜像
docker image rm phase1-rag-api:0.1.0 2>/dev/null || true

# 3) 清掉构建缓存（可选：会释放约 1.8GB，但下次构建变慢）
docker builder prune -a -f

# 4) 删除整个项目目录（含知识库数据，确认不要了再执行）
cd ~
rm -rf ~/phase1-rag

# 5) 清理临时测试文件
rm -f ~/testdoc.md

# 6) 回到第二部分的状态，然后从第六部分重新开始
ls -la ~
```

**只想重置知识库、不删代码**（更常用）：

```bash
cd ~/phase1-rag
docker compose down
rm -rf data/chroma/*        # 清空向量库
rm -rf data/uploads/*       # 清空上传的原始文档
docker compose up -d
```

> **⚠️ `data/` 是唯一不可再生的东西。**
> 代码可以重写、镜像可以重建、容器可以重启 ——
> **但你上传的文档和它们的向量一旦删掉，只能重新上传。**
> 所以 `rm -rf ~/phase1-rag` 之前，先确认里面的文档不需要了。

**验证重置干净：**

```bash
docker ps -a          # 应为空
docker images         # 应只剩 python:3.12-slim（或全空）
ls ~/phase1-rag       # 应提示 No such file or directory
df -h /               # 磁盘应回到 3.7G 左右
```

## A.2 `config.py` —— 配置集中管理

```bash
cat > ~/phase1-rag/backend/app/config.py <<'PYEOF'
"""集中配置：所有可变项都从环境变量来，代码里不写死任何供应商。

当前供应商：阿里云百炼（DashScope 的 OpenAI 兼容模式）
阶段三可切到本地 llama.cpp（同样是 OpenAI 兼容协议），只改环境变量。
"""
from functools import lru_cache
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")

    # ---------- LLM 供应商 ----------
    # cloud = 阿里百炼云端；local = 阶段三的 llama.cpp 本地模型
    llm_provider: str = "cloud"

    # ---------- 阿里百炼（DashScope）----------
    # 一个 key 同时用于 chat 和 embedding
    dashscope_api_key: str = ""
    dashscope_base_url: str = "https://dashscope.aliyuncs.com/compatible-mode/v1"

    # chat 模型：qwen-plus 质量与成本平衡；省钱可换 qwen-turbo
    llm_model: str = "qwen-plus"

    # embedding 模型与维度
    # text-embedding-v4 支持 2048/1536/1024/768/512/256/128/64
    embedding_model: str = "text-embedding-v4"
    embedding_dim: int = 1024

    # 百炼 OpenAI 兼容接口限制：embedding 单次最多 10 行输入。
    # 设大了会直接报错，绝不要改成 1000（langchain 的默认值）。
    embedding_batch_size: int = 10

    # ---------- 本地（阶段三才用）----------
    local_llm_base_url: str = "http://llama:8080/v1"
    local_llm_model: str = "qwen2.5-1.5b-instruct"

    # ---------- 存储 ----------
    chroma_dir: str = "/app/data/chroma"
    upload_dir: str = "/app/data/uploads"
    collection_name: str = "phase1_docs"

    # Upstash Redis（未配置时自动降级为进程内记忆）
    redis_url: str = ""
    memory_ttl_seconds: int = 60 * 60 * 24 * 7

    # ---------- 检索参数 ----------
    chunk_size: int = 800
    chunk_overlap: int = 120
    retrieval_top_k: int = 4

    def memory_backend(self) -> str:
        return "redis" if self.redis_url.strip() else "inproc"


@lru_cache
def get_settings() -> Settings:
    return Settings()
PYEOF
```

### 设计说明

**① 为什么所有配置集中在一个类里？**
如果 `"qwen-plus"` 这种字符串散落在 10 个文件里，
改模型时你要翻遍整个项目。集中在 `Settings` 后，**改一处即可。**

**② `extra="ignore"` 的作用：**
`.env` 里可能有多余的变量（比如以后加的），
不加这个参数 pydantic 会**直接报错**。加上后多余的变量被安静忽略。

**③ `@lru_cache` 是性能与一致性优化：**
它让 `get_settings()` 只执行一次，之后返回缓存对象。
- 性能：不必每次请求都重读 `.env`
- 一致性：全应用共用同一个配置对象

> ⚠️ **副作用（要记住）：** 改了 `.env` 后，**必须重启容器**才生效。
> 热加载不会更新缓存。这就是故障表里"改了 .env 但没生效"的原因。

**④ 为什么 `embedding_batch_size` 的默认值是 10 而不是 1000？**
因为**百炼的硬限制就是 10**。这个默认值写死成 10，
即使 `.env` 忘了配，也不会踩坑。

## A.3 `llm.py` —— 供应商解耦点（**本项目的精髓**）

```bash
cat > ~/phase1-rag/backend/app/llm.py <<'PYEOF'
"""LLM / Embedding 工厂。

这是整个阶段一最关键的解耦点：
业务代码只调用 get_chat_model() / get_embeddings()，
阶段三把 LLM_PROVIDER 从 cloud 改成 local，就能切到 Llama.cpp，其它代码零改动。

两者都走 OpenAI 兼容协议，所以只用 langchain-openai 一个依赖包。
"""
import logging

from langchain_core.embeddings import Embeddings
from langchain_core.language_models.chat_models import BaseChatModel

from .config import get_settings

logger = logging.getLogger(__name__)


def get_chat_model(temperature: float = 0.2) -> BaseChatModel:
    s = get_settings()

    from langchain_openai import ChatOpenAI

    if s.llm_provider == "local":
        # 阶段三：llama.cpp server 暴露 OpenAI 兼容接口
        logger.info("LLM = local llama.cpp @ %s", s.local_llm_base_url)
        return ChatOpenAI(
            model=s.local_llm_model,
            base_url=s.local_llm_base_url,
            api_key="sk-no-key-required",  # llama.cpp 不校验
            temperature=temperature,
            max_tokens=1024,
        )

    if not s.dashscope_api_key:
        raise RuntimeError("LLM_PROVIDER=cloud 但 DASHSCOPE_API_KEY 未配置")

    logger.info("LLM = dashscope:%s", s.llm_model)
    return ChatOpenAI(
        model=s.llm_model,
        base_url=s.dashscope_base_url,
        api_key=s.dashscope_api_key,
        temperature=temperature,
        max_tokens=1024,
        max_retries=2,
        timeout=60,
    )


def get_embeddings() -> Embeddings:
    s = get_settings()
    if not s.dashscope_api_key:
        raise RuntimeError("DASHSCOPE_API_KEY 未配置（向量化必需）")

    from langchain_openai import OpenAIEmbeddings

    logger.info("Embeddings = dashscope:%s (dim=%d, batch=%d)",
                s.embedding_model, s.embedding_dim, s.embedding_batch_size)
    return OpenAIEmbeddings(
        model=s.embedding_model,
        base_url=s.dashscope_base_url,
        api_key=s.dashscope_api_key,
        dimensions=s.embedding_dim,
        # 百炼单次上限 10 行。langchain 默认 1000，不改就一定会在
        # 上传较大文档时报错。
        chunk_size=s.embedding_batch_size,
        # 关闭 tiktoken 预分词：百炼是中文模型，用 OpenAI 的 tokenizer
        # 估算长度既不准也没必要，关掉可省一次 CPU 开销。
        check_embedding_ctx_length=False,
        max_retries=2,
        timeout=60,
    )
PYEOF
```

### 设计说明（**这段最值得学**）

**① 这是"依赖倒置"的实际应用。**
业务代码（`rag.py`）从来不说"我要百炼的 qwen-plus"，
它只说"我要一个 chat model"。**具体是谁，由这个工厂决定。**

结果：阶段三要换成本地模型，**只改 `.env` 一行**，`rag.py` 一个字都不用动。

**② 为什么 `import` 写在函数内部而不是文件顶部？**
```python
def get_chat_model(...):
    from langchain_openai import ChatOpenAI   # ← 在函数内
```
好处是**延迟导入**：只有真正调用时才加载这个模块。
- 加快应用启动
- 如果某个供应商的包没装，**不影响另一条路径**

代价是每次调用都要查一次导入缓存（开销极小，可忽略）。

**③ `chunk_size=s.embedding_batch_size` 是刻意也是必须的。**
这是对百炼 10 行限制的第一道防线。**如果删掉这行，上传较大文档必然失败。**

**④ `check_embedding_ctx_length=False` 为什么关掉？**
langchain 默认会用 tiktoken 把文本预先分词，以估算长度。
但 tiktoken 是 **OpenAI 的分词器**，用于估算**中文模型**的长度既不准、
又白白消耗 CPU。在 891 MiB 的机器上，这点 CPU 也值得省。

**⑤ 报错信息要具体。**
```python
raise RuntimeError("LLM_PROVIDER=cloud 但 DASHSCOPE_API_KEY 未配置")
```
比起裸的 `KeyError`，这种信息能让你**一眼知道该去改哪个变量**。
写代码时多花 5 秒，排查时省 10 分钟。

## A.4 `vectorstore.py` —— 向量库

```bash
cat > ~/phase1-rag/backend/app/vectorstore.py <<'PYEOF'
"""向量库：Chroma 以嵌入式 PersistentClient 方式跑在 API 进程内。

为什么不用独立 Chroma 容器：1 GiB 内存下多一个容器就多 200MB+ 常驻，
嵌入式模式省掉一整个容器的开销，且单机单进程不存在并发写入竞争。
"""
import logging
from functools import lru_cache

from langchain_chroma import Chroma

from .config import get_settings
from .llm import get_embeddings

logger = logging.getLogger(__name__)


@lru_cache
def get_vectorstore() -> Chroma:
    s = get_settings()
    logger.info("Chroma persist dir = %s", s.chroma_dir)
    return Chroma(
        collection_name=s.collection_name,
        embedding_function=get_embeddings(),
        persist_directory=s.chroma_dir,
        collection_metadata={"hnsw:space": "cosine"},
    )
PYEOF
```

### 设计说明

**① `persist_directory` 是"数据不丢"的关键。**
它让 Chroma 把向量数据写到磁盘。而这个路径在 `docker-compose.yml` 里
被 bind mount 到宿主机 —— **所以容器重建不会丢知识库。**

**② `collection_metadata={"hnsw:space": "cosine"}` 为什么用余弦距离？**
文本向量的**方向**比**长度**更有意义。
余弦距离衡量方向差异，不受向量长度影响，是文本检索的标准选择。

**③ 用 `@lru_cache` 让整个应用共享一个 Chroma 客户端。**
Chroma 的 PersistentClient **不允许同一进程内对同一路径开多个实例**
（会报数据库锁错误）。缓存确保只创建一次。

## A.5 `memory.py` —— 对话记忆（**降级设计范例**）

```bash
cat > ~/phase1-rag/backend/app/memory.py <<'PYEOF'
"""对话记忆：优先 Upstash Redis，未配置则降级为进程内字典。

降级设计让你在还没注册 Upstash 时也能先把阶段一跑通，
拿到凭据后只需在 .env 填 REDIS_URL 并重启，代码无需改动。
"""
import json
import logging
import time
from typing import Any

from .config import get_settings

logger = logging.getLogger(__name__)

# ---- 进程内降级实现（单 worker 场景够用；重启即丢） ----
_inproc: dict[str, list[dict[str, Any]]] = {}


class MemoryStore:
    def __init__(self) -> None:
        self.s = get_settings()
        self._redis = None
        self.backend = self.s.memory_backend()

        if self.backend == "redis":
            try:
                import redis as redis_lib

                # Upstash 强制 TLS：rediss:// 开头
                # decode_responses=True 让返回值直接是 str
                self._redis = redis_lib.from_url(
                    self.s.redis_url,
                    decode_responses=True,
                    socket_timeout=5,
                    socket_connect_timeout=5,
                    retry_on_timeout=True,
                )
                self._redis.ping()
                logger.info("Memory backend = Upstash Redis")
            except Exception as exc:  # 连不上就降级，不让服务起不来
                logger.warning("Redis 连接失败，降级为进程内记忆: %s", exc)
                self._redis = None
                self.backend = "inproc"
        else:
            logger.info("Memory backend = in-process (未配置 REDIS_URL)")

    def _key(self, session_id: str) -> str:
        return f"rag:chat:{session_id}"

    def get_history(self, session_id: str) -> list[dict[str, Any]]:
        if self._redis is not None:
            raw = self._redis.get(self._key(session_id))
            return json.loads(raw) if raw else []
        return _inproc.get(session_id, [])

    def append(self, session_id: str, user_msg: str, ai_msg: str) -> None:
        history = self.get_history(session_id)
        history.append({"user": user_msg, "ai": ai_msg, "ts": int(time.time())})
        history = history[-20:]  # 只保留最近 20 轮，控制上下文长度和费用

        if self._redis is not None:
            self._redis.set(self._key(session_id), json.dumps(history, ensure_ascii=False),
                            ex=self.s.memory_ttl_seconds)
        else:
            _inproc[session_id] = history

    def clear(self, session_id: str) -> None:
        if self._redis is not None:
            self._redis.delete(self._key(session_id))
        else:
            _inproc.pop(session_id, None)


_store: MemoryStore | None = None


def get_memory() -> MemoryStore:
    global _store
    if _store is None:
        _store = MemoryStore()
    return _store
PYEOF
```

### 设计说明

**① 这是"优雅降级（graceful degradation）"的教科书例子。**
Redis 连不上时 **不抛异常**，而是 `logger.warning` 后退回进程内字典。
理由：**记忆是增强功能，不是核心功能。**
为了"记忆"这个附加能力让整个服务起不来，是不划算的。

**② `history = history[-20:]` 只保留最近 20 轮。**
因为对话历史会被拼进 prompt 发给 LLM：
- 太长 → 消耗更多 token（花钱）
- 太长 → 上下文超限
- 太长 → 内存与 CPU 压力

**③ `ensure_ascii=False` 为什么重要？**
不加的话，中文会被转义成 `\u4e2d\u6587` 这种形式，
存储体积膨胀数倍。加上后中文原样保存。

**④ `ex=self.s.memory_ttl_seconds`（7 天过期）防止 Redis 无限增长。**
这是免费额度下的必要防护。

**⑤ 注意 `_inproc` 是模块级全局变量。**
它随进程存活，**所以重启容器记忆就没了**。
这是降级模式的固有代价，`/health` 里的 `memory_backend: inproc` 就是在提示你这一点。

```bash
规则：
1. 如果参考资料中没有相关信息，直接回答"知识库中未找到相关内容"，不要编造。
2. 回答时在句末用 [来源N] 标注依据的片段编号。
3. 使用简体中文，条理清晰，必要时用列表。
4. 不要复述规则本身。

【参考资料】
{context}
"""


def _parse_file(path: Path) -> str:
    suffix = path.suffix.lower()
    if suffix == ".pdf":
        from pypdf import PdfReader

        reader = PdfReader(str(path))
        return "\n\n".join((page.extract_text() or "") for page in reader.pages)
    # .md / .markdown / .txt 统一按 UTF-8 读，容错非法字节
    return path.read_text(encoding="utf-8", errors="replace")


def ingest(file_bytes: bytes, filename: str) -> dict:
    """把一份文档切块入库，返回统计信息。"""
    s = get_settings()
    Path(s.upload_dir).mkdir(parents=True, exist_ok=True)

    suffix = Path(filename).suffix.lower()
    if suffix not in SUPPORTED:
        raise ValueError(f"不支持的文件类型 {suffix}，仅支持 {sorted(SUPPORTED)}")

    doc_id = uuid.uuid4().hex[:12]
    stored = Path(s.upload_dir) / f"{doc_id}{suffix}"
    stored.write_bytes(file_bytes)

    text = _parse_file(stored)
    if not text.strip():
        raise ValueError("文件解析后内容为空（可能是扫描版 PDF，需先 OCR）")

    splitter = RecursiveCharacterTextSplitter(
        chunk_size=s.chunk_size,
        chunk_overlap=s.chunk_overlap,
        separators=["\n\n", "\n", "。", "！", "？", ".", " ", ""],
    )
    chunks = splitter.split_text(text)

    docs = [
        Document(
            page_content=chunk,
            metadata={"doc_id": doc_id, "filename": filename, "chunk_index": i},
        )
        for i, chunk in enumerate(chunks)
    ]

    ids = [f"{doc_id}-{i}" for i in range(len(docs))]

    # ---- 显式分批入库 ----
    # 百炼的 OpenAI 兼容 embedding 接口单次最多接受 10 行输入。
    # langchain 的 chunk_size 已经设成 10，但这里再显式分批做双重保险：
    # 即使有人手改 .env 把 EMBEDDING_BATCH_SIZE 调大，也不会整批失败。
    store = get_vectorstore()
    batch = max(1, s.embedding_batch_size)
    for start in range(0, len(docs), batch):
        store.add_documents(docs[start:start + batch], ids=ids[start:start + batch])
        logger.info("  embedded %d/%d chunks", min(start + batch, len(docs)), len(docs))

    logger.info("ingested %s -> %d chunks (doc_id=%s)", filename, len(docs), doc_id)
    return {"doc_id": doc_id, "filename": filename, "chunks": len(docs), "chars": len(text)}


def list_documents() -> list[dict]:
    """按 doc_id 聚合已入库文档（Chroma 没有原生分组，取元数据自己汇总）。"""
    data = get_vectorstore().get(include=["metadatas"])
    seen: dict[str, dict] = {}
    for meta in data.get("metadatas") or []:
        if not meta:
            continue
        doc_id = meta.get("doc_id")
        if doc_id and doc_id not in seen:
            seen[doc_id] = {"doc_id": doc_id, "filename": meta.get("filename")}
    return list(seen.values())


def delete_document(doc_id: str) -> int:
    store = get_vectorstore()
    matched = store.get(where={"doc_id": doc_id}, include=[])
    ids = matched.get("ids") or []
    if ids:
        store.delete(ids=ids)
    return len(ids)


def answer(question: str, session_id: str) -> dict:
    """检索 + 生成，返回答案与引用来源。"""
    s = get_settings()
    store = get_vectorstore()

    hits = store.similarity_search_with_relevance_scores(question, k=s.retrieval_top_k)

    if not hits:
        return {
            "answer": "知识库中未找到相关内容，请先上传文档。",
            "sources": [],
            "session_id": session_id,
        }

    context_parts, sources = [], []
    for idx, (doc, score) in enumerate(hits, start=1):
        context_parts.append(f"[来源{idx}] 文件：{doc.metadata.get('filename')}\n{doc.page_content}")
        sources.append({
            "index": idx,
            "filename": doc.metadata.get("filename"),
            "doc_id": doc.metadata.get("doc_id"),
            "chunk_index": doc.metadata.get("chunk_index"),
            "score": round(float(score), 4),
            "preview": doc.page_content[:160],
        })

    chain = (
        ChatPromptTemplate.from_messages([
            ("system", SYSTEM_PROMPT),
            ("human", "历史对话：\n{history}\n\n当前问题：{question}"),
        ])
        | get_chat_model()
        | StrOutputParser()
    )

    # 历史只取最近 3 轮，避免把上下文撑爆（1 GiB 内存 + 突发型 CPU 额度都要省）
    from .memory import get_memory

    history = get_memory().get_history(session_id)[-3:]
    history_text = "\n".join(f"用户：{h['user']}\n助手：{h['ai']}" for h in history) or "（无）"

    result = chain.invoke({
        "context": "\n\n---\n\n".join(context_parts),
        "history": history_text,
        "question": question,
    })

    get_memory().append(session_id, question, result)
    return {"answer": result, "sources": sources, "session_id": session_id}
PYEOF
```

### 设计说明（RAG 的核心逻辑都在这里）

**① 完整链路要能背下来：**

```
【入库阶段】上传 → 解析文本 → 切片 → 向量化 → 存入 Chroma
【问答阶段】提问 → 向量检索 Top-K → 拼进 Prompt → LLM 生成 → 返回答案+来源
```

**RAG 的本质就是这两段。** 理解了这个，后面的 Agent 都是在此之上加"工具"。

**② 为什么必须"切片（chunking）"？**
- LLM 有上下文长度上限，整本书塞不进去
- 向量检索的粒度越细，命中越准

**③ `chunk_overlap=120` 为什么要有重叠？**
如果不重叠，一个句子可能正好被切在两块的边界上，**两边的语义都不完整**。
重叠 120 字符能让跨边界的信息至少在一块里保持完整。

**④ `separators` 列表里为什么有中文标点 `。！？`？**
这份列表是**优先级顺序**。切分器会先尝试用 `\n\n`（段落）切，
不行再试 `\n`（行），再不行试 `。`（中文句号）……
**因为中文文本里没有空格，如果只用默认的英文分隔符，
会把整段中文当成一个"词"，切分效果很差。**

**⑤ 元数据（metadata）里存了什么，为什么要存：**
```python
metadata={"doc_id": ..., "filename": ..., "chunk_index": ...}
```
- `doc_id` → 让"删除整篇文档"成为可能
- `filename` → 回答时能告诉用户"这句话来自哪个文件"（**这是可信度的来源**）
- `chunk_index` → 定位原文位置，便于排查

**⑥ 分批循环是第二道防线（对应第七部分的坑 1）：**
```python
for start in range(0, len(docs), batch):
    store.add_documents(docs[start:start + batch], ...)
```
即使 `.env` 里的批大小被人改大，**这个循环仍然按 `batch` 切**，不会整批失败。

**⑦ `if not hits` 提前返回 —— 这是防"编造"的第一道闸门。**
如果知识库是空的，**根本不必调用 LLM**，直接返回"未找到"。
省一次 API 调用，也彻底杜绝了空知识库下模型瞎编的可能。

**⑧ `similarity_search_with_relevance_scores` 里的 `_with_relevance_scores`：**
它比普通的 `similarity_search` 多返回一个**相似度分数**。
我们把这个分数放进 `sources` 返回给前端 ——
**用户能看到"这条依据的可信度是 0.87"，而不是只能选择相信。**

**⑨ `chain` 的 `|` 是 LangChain 表达式语言（LCEL）：**
```python
prompt | model | parser
```
管道符表示"把左边的输出作为右边的输入"。等价于：
`parser(model(prompt(输入)))`。**可读性比嵌套调用好得多。**

**⑩ `history` 只取最近 3 轮而不是 20 轮：**
记忆里存 20 轮（供查询），但**拼进 prompt 只用 3 轮**。
因为拼进去的每一轮都在消耗 token 和内存。这是刻意的成本控制。

**⑪ SYSTEM_PROMPT 里的规则 1 是最重要的一句：**
> 如果参考资料中没有相关信息，直接回答"知识库中未找到相关内容"，不要编造。

**这是 RAG 可信度的根基。** 没有这句约束，模型会用训练时的常识
"补全"答案，产生看似合理实则错误的回答 —— 比答不出来危险得多。

### 设计说明

**① 错误处理为什么要分 `ValueError` 和 `Exception`：**
```python
except ValueError as exc:      # 用户的问题 → 400（客户端错误）
except Exception as exc:       # 我们的问题 → 500（服务端错误）
```
**这个区分很重要：** 400 表示"你传的文件不对，改一下再试"；
500 表示"我这边坏了，需要我去修"。
把所有错误都返回 500，会让调用方无从判断该做什么。

**② `logger.exception()` 会记录完整的堆栈。**
用 `logger.error()` 只记录一行消息，排查时你会想知道"到底是哪一行崩的"。
**注意：这里记录堆栈，但返回给用户的只有简短的 `f"入库失败：{exc}"`** ——
不要把内部堆栈暴露给外部调用者（安全考虑）。

**③ `MAX_UPLOAD_BYTES = 20MB` 不是随便定的。**
在 891 MiB 机器上，解析一个大 PDF 会瞬间吃掉几百 MB 内存。
限制 20MB 是**保护机器不被单个请求打垮**。

**④ `session_id` 的默认值设计很巧妙：**
```python
session_id = req.session_id or uuid.uuid4().hex[:16]
```
- 前端传了 → 用它（多轮对话共享记忆）
- 前端没传 → **自动生成一个**（不会因为缺参数而报错）

**⑤ `Field(min_length=1, max_length=2000)` 是自动校验。**
FastAPI 会**在进入函数体之前**就校验参数。
超长或空的问题根本不会执行到业务逻辑，直接返回 422。

**⑥ CORS 的 `allow_origins=["*"]` 只适合开发期。**
上线要收紧成具体域名。注释里写明了这一点 —— **好的代码会标注"这里以后要改"。**

**⑦ `/health` 返回 `llm_provider` 和 `memory_backend`。**
这个小设计在实际运维中极其有用：**一眼看出当前用的是哪套配置**。
排查"为什么记忆没了"时，看到 `memory_backend: inproc` 就立刻明白了。
